# 2026.317.2115 — feat(step)!: the plugin tree's sources come from the engine, not a store scan

## Summary

`step:plugin-tree` could not find a built plugin on a current charly. It scanned `~/.cache/charly/plugins` — a directory the product no longer writes — and refused every run:

```
plugin-tree: plugin-firecracker: no built plugin in /home/atrawog/.cache/charly/plugins
             - refusing to deliver a tree without it
```

The refusal was the step behaving correctly (`fill-first`: deliver nothing rather than a tree missing a member). The defect was upstream of it: **the scan itself**. Three store paths, one engine store (`sdk/buildcache`), and a newest-wins tie-break that answered "which binary is this plugin?" by modification time — over a layout this plugin does not own, on a machine (`kind: cloud_image`) where the store does not exist at all.

The deploying charly already knows the answer, because it resolves the served binary when it **connects** the plugin: `plugin <ref>: served from <path> (build <sha256>); source <dir>`. `opencharly/charly#1131` made the engine hand that set over (opencharly/charly#1134); this change consumes it.

- **The step declares `PluginPaths: true`** on its `class:step` contract — what makes the host inject the connected plugin set into this step's input under `spec.ConnectedPluginsInputKey` (`"plugin_paths"`). Declared in the SERVED capability, not only in Go: the host acts on the declared contract.
- **`plugin_paths` is declared in the plugin's own schema** (`#PluginTreeInput` → `#PluginTreeSource`, self-contained, importing nothing), because the input is validated against it.
- **Each authored `plugins: [<leaf>]` is resolved against that set by LEAF**, delivered from the `view_path` the engine named. `plugins: [<leaf>]` stays the authored spelling; `buildcache` gains no lookup-by-name heuristic.
- **`pluginStoreDir()`, its `CHARLY_PLUGIN_STORE` override and the directory scan are DELETED.** That deletion is #1131's observable.
- **The bed composes the plugin it delivers.** `plugin-tree-vm-host` now carries `@…/plugin-firecracker:v2026.288.0016` (a released tag, for reproducibility). The engine can only hand over what its connect resolved, and the old scan is what let this bed name a plugin the deployment never carried.

Three refusals, all `fill-first` and all named: no connected set at all (an engine older than the release that supplies it), a name the engine did not connect (the message lists what it DID connect), and a leaf the engine connected **twice** — that one refuses rather than choosing by modification time, because choosing is the guess this change removes.
