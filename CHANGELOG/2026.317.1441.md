# 2026.317.1441 — fix(plugin): deliver the tree to the venue, not to this process (supersedes #15)

## Summary

`step:plugin-tree` filled `StablePluginsPath` with `os.WriteFile`, so it wrote to the machine the **plugin** runs on rather than the venue. Correct where those are the same machine; wrong whenever they are not. **Reopens #10.**

**The write now goes through the venue executor:**

    ex, err := sdk.ExecutorForInvoke(ctx, req.GetExecutorBrokerId())
    for _, p := range planned {
        data, err := os.ReadFile(p.src)                        // local: the store is where charly built it
        if err := ex.PutFile(ctx, p.dest, data, 0o755, false); err != nil { … }
    }

`PutFile` is `os.WriteFile` on a `host: local` venue and scp-plus-install into the guest on a `vm:` one. The local `os.ReadFile` stays — the store is where the *deploying* charly built the plugin.

**What this round (2026-11-13) adds.** The second BLOCK on this head named the one cure this repository can hold, in its own words: *"a fake/`host: local` executor asserting `PutFile` receives the planned `dest`+`content` and failing on the old `os.WriteFile` — so the 'cannot be expressed in-repo' claim does not discharge R10."* Its finding 2 offers the same control as the alternative that makes the gate *"green and distinguishing in-repo"*. **That control now ships in the diff**, and it fails without each half of the change.

**Every file in the diff, accounted for** — `git diff --stat origin/main...HEAD` on this head, 4 files, +172/−6:

|---|---|
| `candy/plugin-deploy-firecracker/plugin_tree_test.go` **(new, +137)** | the discriminating control: a fake `ExecutorServiceClient` (it embeds the generated interface and overrides **only** `PutFile`, so any other venue call panics rather than passing silently) wrapped by `sdk.NewInProcExecutor` + `sdk.ContextWithExecutor`; asserts the delivered `dest` (the **leaf** name the loader opens, not the store's hash-suffixed entry), the exact bytes (binary-safe), the `0o755` mode and `ownerRoot=false`; then asserts the **fill-first** refusal — a name with no built plugin delivers **nothing** |

**Why the two `plugin.go` edits ride with the test.** `ExecutorForInvoke` is the **transport-invisible** resolver (in-proc compiled-in placement → the context; out-of-process → the broker id). Calling `ExecutorFromInvoke` directly dials the broker only, so the same handler would fail outright on a compiled-in placement — a latent defect, and also the reason the handler could not be driven by an in-proc fake. It is the same route the SDK's own `LandArtifact` venue path takes. The deleted `os.MkdirAll` created `stablePluginsPath` **on this process's filesystem** before writing into it — a directory on the wrong machine; under venue delivery both `ShellExecutor.PutFile` (`spec/exec/deploy_executor.go:75`) and `SSHExecutor.PutFile` (`deploy_executor_ssh.go:138`) use `install -D`, which creates the parent **at the venue**.
