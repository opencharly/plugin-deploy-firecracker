# 2026.318.0132 — feat(step)!: the delivered tree carries its manifest, and the step verifies the delivery

## Summary

`step:plugin-tree` delivers a plugin tree — the binaries a later step's bare command/verb WORD resolves through. It wrote the binary and then the `<leaf>.providers` manifest as **two `PutFile` calls and never checked what landed**, so a partial delivery was invisible to the step and could only surface later as a bed mystery. This leg closes that and completes the tree's contract:

- **`<leaf>.providers` is written beside every delivered binary**, from `spec.PluginManifest` (the ONE serializer the baked-image emitter uses too, opencharly/spec#313) using the words the ENGINE connected (`plugin_paths[i].providers`, opencharly/charly#1140) — the step never re-derives what a plugin serves.
- **The step READS BACK what it wrote.** After delivering, it `GetFile`s both files, requires the manifest's bytes to equal what it wrote, and FAILS LOUDLY by name if either is missing or wrong. A partial delivery is now a step failure at the moment it happens, naming the file — not an intermittent gate for a later assertion to reconstruct.
- **The bed asserts RESOLUTION in BOTH its phases, not existence.** `test -x` is what let the original defect through: a tree of binaries with no manifest answers every invocation with charly's usage text while every file it needs is present. The beds now assert the manifest is there, that it declares the expected word, and that `charly <word> --help` actually RESOLVES against the delivered tree inside the guest — and they print the delivered tree listing and the exact invocation in the PASS path too, so a witness is diagnosable when it succeeds.
- **Pins:** `spec v0.2026317.2143` (the field + the serializer) and `sdk v0.2026317.2240` (the released repoint of the baked manifest writer).

The handler's comment now names all THREE refusal conditions with their provenance: no connected set (new), a name the engine did not connect (the inherited fill-first refusal, re-sourced from the engine's resolution), an ambiguous leaf (new — the old store scan silently took the newest match) — plus the new read-back failure.

- **R1 how (evidence: the `## How tested` blocks above):** one arm of this bed observed the binary present and the manifest missing (calver `2026.317.2220`). Two findings, and this body does not confuse them: **(a) the step could not tell** — it wrote two files with no read-back, so a partial delivery was reported as success; that is FIXED here (read-back, byte comparison, loud refusal by name, with a `partialVenue` arm proving it). **(b) why the manifest went missing is NOT established.** The executor returns success from `PutFile` and retains no record of what it wrote, and the runner keeps only a failing step's stderr tail, so neither a dropped write nor a visibility race can be decided after the fact. Detection is not prevention, and five green runs are not an explanation — so the undecidable half is FILED: opencharly/spec#315 (executor write journal / verified `PutFile`) and opencharly/charly#1141 (the truncation).

## Filed issues

- **opencharly/spec#315** — a venue `PutFile` reports success with no retained record of what it wrote, so a dropped delivery is undecidable afterwards. Non-blocking here: this PR makes a partial delivery DETECTED and named by the step, which is the defect it owned; the executor's own observability is separable and lives in `spec/exec`.
- **opencharly/charly#1141** — `charly check` keeps only a failing step's stderr TAIL, so a bed cannot show the evidence that decides its own assertion; it cut the line that would have named which manifest assertion fired.
- **opencharly/plugin-deploy-firecracker#18** — the defect this PR CLOSES (a delivery that reported success without checking the manifest arrived).

## Change classification

- **Class:** plugin behavior change (step handler gains manifest delivery, read-back verification and a fourth refusal condition; both beds gain resolution assertions) with `spec`/`sdk` pin bumps.
- **Breaking change + rollback:** yes, deliberately: a deployment whose engine predates the connected set (or predates the provider words) now REFUSES, loudly and by name, where the old step scanned a directory. Rollback is `git revert` plus the pins returning to their previous values — and a reverted step goes back to a scan that cannot find a built plugin on a current charly, i.e. back to the defect, not to a working alternative.
- **Producer ordering:** `spec v0.2026317.2143` (spec#313) and the `charly` engine half (charly#1140, which carries the words) are the producers; this leg is their consumer; `plugin-firecracker#11` and `layer-fireactions-runner#2` follow this release and stay untouched here.
