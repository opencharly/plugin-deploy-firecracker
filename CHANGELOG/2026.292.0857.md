# 2026.292.0857 — feat(plugin): copy the named plugins into the loader's stable path

## Summary

**What this actually does: it copies the named plugins into the loader's stable path, and stops
there.** It does **not** make them usable — the variable that points the loader at that path is not
set by this step, and is filed as `opencharly/charly#977`. The usability proof belongs to a consumer
that composes this plugin, names the tree and invokes it.

**Why the copy exists.** `charly firecracker` is an out-of-process command plugin, so a plugin-backed
plan step needs a plugin tree at the venue. Measured on a live `kind: cloud_image` guest: no
`CHARLY_PLUGIN_DIR`, no `/tmp/charly-plugins`, while its charly binary is present and working. The
one delivery mechanism that existed writes the variable into a Containerfile at image-build time,
and that guest is not built from one.

**What that measurement does NOT establish, and this PR does not claim:** that a delivered tree makes
the verb resolve at such a guest. On the only venue this PR proves — `host: local` — the deploying
store **is** the loader's store, so the copy is redundant there and the bed confirms a file landed,
nothing more. That is a claim about a copy, and it is the claim made.

| file | change |
|---|---|
| `candy/plugin-deploy-firecracker/plugin.go` | the `step:plugin-tree` capability with its `StepContract`, the `req.GetClass()` dispatch, and the handler |
| `candy/plugin-deploy-firecracker/schema/firecracker.cue` | `#PluginTreeInput` — the plugin names to copy |
| `candy/plugin-deploy-firecracker/charly.yml` | the step joins the providers list; the remit sentence names both classes; the plan's check verifies **both** classes; and the candy's plan authors `run: plugin-tree:` plus a paired assertion |

**The handler**, exactly as written: it takes the plugin names from the consumer; for each name it
reads the deploying charly's plugin store (`CHARLY_PLUGIN_STORE`, or `~/.cache/charly/plugins`) and compares every entry's leaf segment **exactly** — after
trimming the `.lock`/`.stamp` sidecars and cutting the final `-<build key>` — so a different plugin
whose leaf merely *begins* with the requested one cannot be delivered under the wrong name; it
**refuses when it finds none**, and selects the newest when several builds are present; it copies the
chosen binary to `StablePluginsPath` under the leaf name the loader keys a plugin by.

**It does not set `CHARLY_PLUGIN_DIR`.** An earlier version appended to `~/.profile` and `~/.bashrc`;
that was an R3 shim and was removed. Nothing in this change reads or writes any shell startup file.

**What the bed proves, and what it cannot.** It proves the step dispatches at a real venue, finds the
named plugin, and writes it under its leaf name — and it fails without each of those: the
no-hash-suffixed-sibling assertion fails on an earlier handler that copied the store's filename
verbatim, and the plan's own check greps for the capability word, the handler and the contract, so
removing the step class fails it (verified by deleting the capability, running the check's command,
seeing it fail, and restoring the file).

**It cannot prove the scenario the copy exists for.** On `host: local` the deploying store is the
loader's store, so the bed cannot distinguish "the copy worked" from "the file was already there".
Proving delivery on a store-less venue, and proving that a delivered tree makes the verb resolve,
both need a consumer — which is why the usability proof is the consumer bed's, not this one's.
